## 確認した構成と信頼境界

現在の実行経路は次のとおりです。

```text
Internet
  -> frontend nginx :443
      -> public FastAPI backend :8000
          -> PostgreSQL
          -> Bearer認証付きrunner API :8001
              -> rootless Docker socket
                  -> sandbox container
```

確認した主な境界:

- frontendだけがComposeからhostへ公開される
- backendにDocker socketはない
- runnerだけがrootless Docker socketを持つ
- runnerとDBは別々の`internal` networkにある
- sandboxはnetworkとIPCを分離し、host bind mountとDocker socketを持たない
- commandとproblem inputはrequest固有のin-memory archiveとして渡す
- 実行結果はbackendへ返った後、judgeとDB保存へ進む

この分離により、通常のbackend侵害から任意Docker APIへ直接進む経路は
以前より縮小しました。一方、runner、DB、frontendは同じrootless daemonとVMを
共有するため、runner侵害またはcontainer escape後の影響範囲は共有されます。

## 主要な新規発見

### High: 動的sandboxログがoutput limitを迂回する

`ContainerManager`が動的に生成するsandboxは、logging driverを指定していません。
開発環境ではdaemon既定の無制限`json-file`を継承していました。

shell commandがPID 1のstdout/stderrへ数byteのmarkerを書いた場合、
Docker execのresponseは通常の文字列だけを返す一方、markerは
`container.logs()`へ記録されることを確認しました。

この経路は、runnerの`BoundedByteBuffer`とoutput overflow時killを通りません。
実際の大量出力は行っていませんが、host側Docker storageとI/Oを消費できるため、
High、P0、公開前blockingと判断しました。

### High: crash後のdeadlineとorphan回収がない

watchdogはrunner内threadです。runnerが異常終了するとdeadlineも失われます。
管理labelは付いていますが、startup時の残存container回収はありません。

また、Docker SDKの`containers.run()`はcreateとstartを内部で連続実行します。
create後のstart失敗または応答timeoutでは、呼出側がcontainer参照を得られず、
process内の管理辞書へ登録できない可能性があります。

graceful shutdown時も、まだ動いているworkerのremoveとpool shutdownのremoveが
競合し、Docker 409を返す経路を非破壊的testで確認しました。
test後の残存containerは0件でしたが、設計上のfailure pathは残っています。

### High: 問題一覧の同期parse

`GET /api/problems`は、requestごとに92 YAMLを同期open・parseします。
handlerは`async def`で、処理中は単一event loopを占有します。

監査時の測定では、92 filesの読込が平均約40 ms/requestでした。
nginxの同一client上限20 requests/secondに対して十分高コストであり、
単一送信元や複数送信元からbackend全体を遅延させられます。

### High: nginxの全体tokenを不正requestが消費する

`/api/shellgei`のfrontend全体1 request/secondのtokenは、
HTTP method、JSON、schema、登録済みproblemの検証前に消費されます。
GET、OPTIONS、不正JSON、未知problem等、Dockerを開始しないrequestでも
正規実行のtokenを消費できます。

runner側のtoken bucketは、認証、schema、problem確認後に適用されます。
Docker開始頻度の正本としてはこちらが適切です。

## 既知問題の再評価

### Resolved

- host共有temporary file
  - request固有in-memory archiveへ移行し、並行requestの混入経路を解消
- rootful/TCP Dockerへの誤接続
  - Compose wrapperとrunner startupでfail-closed
- writable sandbox root layer
  - read-only rootと容量・inode制限付きtmpfsへ変更
- CPU、memory、PID制限の見かけだけの適用
  - rootless cgroup v2/systemdを必須化し、実container値を検証
- silent commandとbackground process
  - watchdog、container kill、使用済みcontainer破棄を実装
- problem ID path traversalと巨大command
  - Pydanticと内部処理で再検証
- DB execution logとCompose service logの無期限累積
  - DB期間・件数、Compose log rotationを実装
- 公開backendのDocker socket
  - 認証付き固定schemaの内部runnerへ分離

### Partially resolved

- sandbox container hard cap
  - 1 process内の管理対象は3件だが、crashとcreate/start曖昧失敗は未管理
- filesystem消費
  - 現在のimageではread-only rootとtmpfsが有効だが、可変imageの
    `VOLUME` metadataと匿名volume cleanupをfail-closedで確認していない
- cgroup実効値
  - 現在のimageでは確認したが、検査がimage内`/bin/sh`と`cat`を信頼する
- persistent log
  - Compose serviceはrotation済みだが、動的sandbox loggingが未制限
- DoS admission control
  - runner開始頻度・同時実行は制限したが、HTTP受付、event loop、I/O、
    複数host間の公平性に残存経路がある

  完全には固定されていません。
