# 問題作成ガイド

この文書は、問題の新規作成・修正時に参照する設計方針の正本です。
良いシェル芸問題を、**入力の構造を見抜き、小さな道具の働きや組み合わせを発見できる問題**とします。
正解を出せることに加え、「この問題で何を体験してほしいか」を説明できるようにします。

データの書式・判定仕様は[問題データ仕様](../problems/README.md)、
公開される情報は[API仕様](API.md)、実行環境は
[sandbox README](../deploy/sandbox/README.md)と[セキュリティモデル](../SECURITY.md)を参照してください。
このガイドの設計メモを、そのまま問題YAMLの新しいfieldとして追加してはいけません。

## 作問の背景と今後の方針

作者による補足として、既存問題は必ずしも「何を学んでほしいか」を十分に整理して作られたものではありません。
参照解答にawkが多いのは、作成時に作者がawkでの解法を主に思いついたためであり、
awkを中心に使ってほしいという出題方針ではありません。
既存の参照解答を推奨する唯一の解法と扱ったり、後から学習意図を推測して作者の意図と説明したりしないでください。

今後は作者とCodexの双方が、学習・発見してほしい内容から問題を設計します。
一般的なUnix/Linux環境で日常的に使われるコマンドを幅広く学び、用途に応じて選び、
組み合わせられる問題群を目指します。ここでいう「標準的」はPOSIX規格への適合だけを意味せず、
実際に使えるコマンドやオプションは本サービスのsandboxで確認します。
Codexは最初に思いついたawk解で検討を終えず、小さな専用コマンドで自然に表現できないかも探してください。
awkも大切な道具の一つとして扱い、使用を避けることや別のコマンドを無理に使わせることは目的にしません。

## 既存問題から分かること

以下は2026-09-06、commit `31d911e`時点の調査です。
`problems/v3/`の全92問の日本語問題文・参照解答を読み、代表例の入力・期待出力を照合しました。
設計上の評価は参照解答から読み取ったもので、元の作者の意図を断定するものではありません。
問題を追加・修正するときは、以下の集計だけに頼らず、その時点の問題群を確認してください。

### 構成と偏り

| 区分 | 問題数 | 主な傾向 |
| --- | ---: | --- |
| STANDARD | 51 | 入出力入門、数値計算、アルゴリズム、文字列変換、模様の生成。参照解答の41問にawkが登場する |
| PRACTICE | 36 | コマンド名を明示する基礎練習。awk 8、sed 6、cat・grep各4、echo・find・sort・wc各3、uniq 2問 |

入力は68問が`input.txt`を1つ持ち、24問がfixtureなしです。標準入力を設定した問題はありません。
fixtureなしでも、問題文の条件や環境内のデータを使う問題があります。

| 参照解答に登場するコマンド | 問題数 |
| --- | ---: |
| awk | 49 |
| sed | 20 |
| sort | 12 |
| xargs | 8 |
| grep、tr | 各6 |
| uniq、convert | 各5 |
| find | 4 |
| cut、seq、factor | 各2 |
| rs | 1 |
| paste、comm、join、head、tail、tac、rev、fold | 各0 |

同一コマンドが1問に何回登場しても1件とし、`xargs`から呼ぶ`grep`も含めます。

入力を渡すための`cat`や、awk内の`printf`などはこの表から除いています。

参照解答では、grepへの過度な偏りよりも、awkでループや条件分岐を書く例の多さが目立ちます。
これは解答例の傾向であり、各問題がawkを要求していることや、他の道具では解けないことを示しません。
列の入れ替えや文字から行への変換はありますが、2つのデータの集合演算・キー結合は手薄です。
複数fixtureを使う問題もなく、ファイル探索は主にShellGeiDataを対象にしています。

### 基礎練習・重複・見直しの観点

- `PRACTICE-grep-*`、`PRACTICE-sort-*`などの単独操作は、基礎練習として役割があります。
  新しく同種の問題を増やす場合は、既存の練習では学べない内容を示してください。
- [PRACTICE-sort-03](../problems/v3/PRACTICE-sort-03.yaml)と
  [PRACTICE-uniq-01](../problems/v3/PRACTICE-uniq-01.yaml)は、異なる道具で整列・重複除去を扱います。
  比較学習には使えますが、数値と単語を変えただけの追加は学びが重なります。
  `PRACTICE-awk-04`と`PRACTICE-wc-01`の行数、`PRACTICE-awk-05`と
  `STANDARD-00000003`の列生成にも同様の重なりがあります。
- [STANDARD-00000010：虫食い日記](../problems/v3/STANDARD-00000010.yaml)は、指定された語を
  指定箇所へ埋める作業が中心です。応用問題を追加する際の手本にはせず、置換の基礎練習と区別します。
- [STANDARD-00000017](../problems/v3/STANDARD-00000017.yaml)はsortを、
  [STANDARD-00000020](../problems/v3/STANDARD-00000020.yaml)はfactorを使わない課題です。
  アルゴリズム学習としての意味はありますが、Unixの道具を発見する目的とは別です。
  新問では便利な道具を禁止して難しさを作ることを標準にしません。
- [STANDARD-00000024：ナップサック問題](../problems/v3/STANDARD-00000024.yaml)や
  [STANDARD-00000026：最短経路探索](../problems/v3/STANDARD-00000026.yaml)の参照解答は
  awk内の多重ループや状態管理が中心です。単に一般のプログラムをawkへ移した問題を増やさず、
  awkの連想配列やストリーム処理を選ぶ意味を説明します。
- [STANDARD-00000030：シーザー暗号](../problems/v3/STANDARD-00000030.yaml)の参照解答は
  文字ごとの長い分岐ですが、文字集合の対応として考える余地があります。
  参照解答が長いことだけで題材の価値や難易度を決めず、自然な別解を探します。

これらは今後の設計判断の材料です。このガイドの追加を理由に既存問題を削除・改題したり、
参照解答をまとめて書き換えたりしません。

## 設計の原則

### 1. 最初に発見を一文で書く

問題文やランダムな入力より先に、「何を知り、どう見方が変わるか」を決めます。
「pasteを使う」だけでは足りません。「同じ行番号の値を横に並べれば、別々の列を1つの記録として扱える」
のように、入力の構造とコマンドの機能を結び付けます。

核の候補には、集計、集合演算、キー結合、除外・抽出、文字集合の変換、引数化、
列生成、整形、行・列・文字・複数行レコードの見方の切り替えがあります。
使用コマンドの候補から考え始めてもよいですが、その操作が自然に必要になる題材を選んでください。

### 2. 自然な簡潔さを選ぶ

素朴にはループ、手作業、状態管理が必要な処理を、道具の機能へ任せられると学びになります。
比較対象は考え方を説明するために使い、「Pythonなら何行」といった行数競争にはしません。
パイプの段数や文字数ではなく、各段に役割があり、変換の流れを追えることを重視します。

`sort -u`や`tr`だけで十分なら1コマンドで構いません。
逆に、複雑な正規表現、珍しいオプション、長いawkプログラムだけを難しさの根拠にしません。
awkの連想配列による集計など、awk自体の強みが核ならawkだけの解も歓迎します。

### 3. 入力に必要性と反例を持たせる

ログ、TSV、単語列、売上、センサー値、日時、ファイル一覧など、構造が理解できる題材を選びます。
実データらしさは必須ではなく、ビット列や行列のように変換の意味が明確なら十分です。
ドメイン知識が必要な計算式や用語は、問題文だけで理解できるように説明します。
個人情報や秘密情報を実例に使わず、必要な構造を保った架空データにします。

入力は小さく読み切れる量にし、核となる発想の必要性が見える値を選びます。
数値ソートなら桁数の違う値、頻度集計なら離れた重複、ランキングなら同率など、
よくある誤解を区別できる例を含めます。全ての境界条件を無理に1問へ詰め込みません。
現在の判定は固定データなので、設計時だけ検討した反例が非公開テストとして実行されるわけではありません。

区切り、ヘッダー、空行、空白を含む値、重複、大小文字、文字コード、出力順、同順位、
丸め方を必要に応じて定義します。CSVを単純なカンマ分割で扱うなら、引用符や値中のカンマを
含まない形式であることを明示します。データの前提を、想定解の都合で隠してはいけません。

### 4. 解き方を閉じず、結果を明確にする

参照解答は一例です。coreutils中心、grep/sed/cut中心、awk中心などの自然な別解を検討します。
短い別解で想定コマンドが不要になっても、同じ学びや新しい発見があるなら価値があります。
入力がたまたま整列済みで処理そのものが不要になるなど、狙いを体験しなくても済む偶然は見直します。

現在のjudgeは、提出されたコマンドの構文や使用コマンドを採点しません。
参照解答と期待出力も公開され、固定出力の直書きを完全には防げません。
「このコマンドで練習する」は学習上の案内であり、システムが強制する制約と説明しないでください。
抜け道対策のためにコマンド禁止やソース検査を追加することは、通常の問題作成の範囲外です。

### 5. 難易度と配置を分けて考える

設計メモには総合的な目安と、その理由を次の軸で記載します。

| 軸 | 判断すること |
| --- | --- |
| コマンド・オプションの知識 | 基本操作か、新しい道具や機能を知る必要があるか |
| データの見方 | 行のまま扱えるか、列・文字・集合・レコードへ捉え直すか |
| 分解と組み合わせ | 各段を素直につなげるか、中間表現を考える必要があるか |
| 境界条件 | 順序、同率、空値、数値表現などをどれだけ考慮するか |

珍しいオプションを知っているだけで解ける課題を、それだけで上級扱いしません。
初級は基礎操作または1つの見方、中級は意味のある組み合わせ、上級は複数の見方や条件の整理を目安にし、
利用者が前提として知っていることを併記します。難易度をYAMLへ独自追加してはいけません。

### 6. 既存問題との差と問題群の役割を示す

最も近い既存問題をID付きで挙げ、「入力構造・変換・主要コマンド・発見」の4点で比較します。
数値、単語、背景設定だけを変えたものは原則として追加しません。
同じコマンドでも、全体集計と連続区間の集計のように異なる意味を学べるなら区別できます。
基礎から応用への段階を作る場合も、前の問題から何が増えたかを明示してください。

次に補う候補は、単純なコマンド登場数より、次の体験の不足から考えます。
これは問題案や実装予定の確定ではありません。

| 観点 | 既存の状況と補う方向 |
| --- | --- |
| 抽出・変換 | grep/sedの基礎がある。単なるパターン変更より、抽出結果を次の処理へ渡す意味を持たせる |
| 集計・並べ替え | uniqやランキングがある。連続性、安定性、集計単位の違いを体験できるかを見る |
| 集合・結合 | comm/joinの参照解答がない。集合の差とキー結合を別の概念として扱う |
| 列・構造の組み替え | awkの列操作とrsがある。paste、fold、tac、revなどで見方を変える余地がある |
| 数値処理 | アルゴリズム問題が多い。計算そのものより、計算結果とテキスト処理をつなぐ意味を見る |
| ファイル操作 | findと外部データの検索がある。管理された小さなfixtureで探索や引数化を学べるかを見る |
| 画像 | convertの描画が中心。テキストや数値から描画条件を組み立てるなど、組み合わせの意味を見る |

各コマンドを均等に出す必要はありません。問題群を通じて、Unixの小さな道具を組み合わせる文化が
伝わることを目指します。

## ファイル作成前に提示する設計メモ

Codexは、問題データを作る前に次の設計を依頼者へ提示してください。
新規作成では全項目、既存問題の修正では確認できる元の狙いと変更する項目・影響を明確にします。
元の狙いが未整理なら、その旨と今回提案する学習意図を分けて記載します。
このメモは提案・レビュー用であり、提出者向けの問題文へ解法の説明を全て混ぜるものではありません。

```text
仮題・配置候補：
問題の狙い／学習・発見してほしいこと：
想定する主要コマンドと必要な機能：
Unix的な考え方／入力をどう捉え直すか：
素朴な解法では何が面倒か：
シェル芸にするとどこが簡潔・面白くなるか：
入力の構造・前提／出力の規則：
想定解と各段の役割：
自然な別解とその発想（未検証なら明記）：
難易度の目安・各軸の理由・前提知識：
最も近い既存問題のIDと具体的な差：
問題文・データの自然さ／基礎練習ならその位置付け：
誤解を区別する入力・境界条件／期待出力の独立した確認方法：
sandbox・画面・判定との適合／必要な変更と検証範囲：
```

学びや既存問題との差が説明できなければ、入力を量産せず核から再検討します。
自然な別解が見つからない場合も、無理に不自然なパイプラインを作らず、探索結果を記載します。
相談・設計だけの依頼では、このメモまでで止めます。

## 作成後に残す短い記録

問題を作成したら、採用した設計意図を`docs/problem-design-notes.md`へ問題IDごとに記録します。
この文書は最初の新問を作成するときに用意し、以後は同じ文書へ項目を追加します。
会話内の提案だけで終わらせず、問題データと同じ変更に含めてレビューできるようにしてください。

各項目は次の形式を目安に、箇条書き5項目程度で簡潔にまとめます。

```markdown
## 問題ID：問題名

- 問題データ：該当するYAMLへの相対リンク
- 狙い・発見：何を学び、どのようにデータの見方を変えてほしいか。
- 解法の核：主要コマンドと組み合わせる意味。確認した別解があれば、その発想も一言。
- 入力の意図：このデータや境界条件を選んだ理由。
- 難易度・既存との差：前提知識と、近い既存問題のID・新しく体験できること。
```

問題文・入出力・参照解答の全文はコピーせず、YAMLを正本として参照します。
採用しなかった案や会話の経緯も転記せず、完成した問題の意図を残します。
問題を修正して狙いや解法が変わった場合は、対応する記録も更新してください。
既存問題の記録を後から作る場合は、作者が確認した意図と、新たに提案する学習意図を区別します。
記録を埋めるために既存92問の作成意図を推測して一括追加する必要はありません。

## 現在の実装に合わせるための確認

### データ・表示・判定

- 本番の定義は`problems/v3/`です。field、ID、fixture、画像、manifestの具体的な規則は
  [問題データ仕様](../problems/README.md)に従います。テキスト問題にも対応JPEGが必要な現行構成を確認します。
- 問題文は日英それぞれで、同じ前提・順序・数値条件を伝えます。
  [問題画面](../frontend/src/tsx/problem.tsx)は改行を保ったプレーンテキスト表示で、Markdownを解釈しません。
  長い横並びやMarkdown表に頼らず、スマートフォンでも条件を追える短い段落にします。
- [問題詳細APIへの変換](../backend/soj_shared/problem_repository.py)は`input.txt`だけを入力欄へ渡します。
  schemaにある複数fixtureや標準入力は自動で一覧表示されません。
  利用するなら、問題文で必要なpath・内容・入力方法を漏れなく提示できるか確認し、
  難しい場合は表示機能の変更を先に別途整理します。
- 空の入力・期待出力は、現在の画面では`NULL`と表示されます。
  これは空を示す表示であり、データに文字列`NULL`を入れる指示ではありません。
- [text judge](../backend/soj_backend/judge.py)の正規化を踏まえ、区別されない末尾空白やCRだけを
  正誤の核にしません。行内部の空白、タブ、出力順などの必要条件は明確にします。
- 既存92問の`exit_code: ignore`、`stderr: merge`は移行時の互換方針です。
  新問では終了code・標準エラーの扱いを意図して決めます。正常終了・標準出力だけを学ぶ問題なら
  `zero`と`must_be_empty`を候補にし、正常な「該当なし」などの終了codeも検討します。
  既存問題のpolicyをついでに変更しません。
- 画像問題の画素一致と、生成GIFのUI表示は別の仕様です。
  GIFが表示されるだけで画像問題の正解になるわけではありません。
  判定用形式・path・正解画像・表示用JPEGを確認し、見た目だけでなく実judgeで検証します。
  JPEGの再圧縮、フォントや描画方法の違いで自然な別解が失敗しないかも確認します。

### 再現できる実行環境

- 利用可能なコマンドは[sandboxの構成](../deploy/sandbox/README.md)と
  [Dockerfile](../deploy/sandbox/Dockerfile)で確認します。
  Ubuntuという理由だけで、Python、jq、開発環境などが使えると仮定しません。
  未導入のコマンドが必要なら、依存追加・検証の範囲を設計メモに記載します。
- 入力、途中の出力、完成した出力、実行時間が[APIの制約](API.md)と
  [sandboxの制限](../SECURITY.md)内に収まることを確認します。
  schemaの文字数・byte数上限を満たすだけでは、ブラウザから提出可能とは限りません。
  最終出力が短くても、膨大な中間データやプロセスを生成する解法は避けます。
- 実行時の外部ネットワーク、sudo、ホストのファイル、前の提出の状態を前提にしません。
  日時、乱数、列挙順、locale、環境固有の表示にも注意し、必要なら条件を固定・明記します。
  制限を緩めて参照解答を通すことはしません。
- ShellGeiDataはbuildごとに最新を取得する構成です。
  利用時はpathと必要な内容を確認し、検証したsandbox image IDとデータrevisionを記録します。
  将来のbuildでも同じ内容とは仮定せず、可能なら管理されたfixtureで成立する設計を優先します。

## 作成・検証の進め方

1. 最新の問題群、関連実装、上記の正本文書を確認し、近い既存問題と不足する体験を探します。
2. 解法の核を決め、設計メモを提示します。問題作成まで依頼されている範囲で次へ進みます。
3. 入力と期待出力を設計し、手計算・別の考え方などで期待値を独立に確認します。
   参照解答の出力を無条件に正解データへコピーしません。
4. データファイルを追加・修正する前に、以下の既存baseline検査への影響を整理します。
   データ・検査・manifestを合わせてレビュー可能な変更にします。
5. [問題データ仕様](../problems/README.md)に従って定義と画像を用意し、manifestを再生成します。
   無関係な問題の意味や期待出力を変えていないことをdiffで確認します。
6. [開発手順](DEVELOPMENT.md)に従い、schema、repository、問題データの検査を行います。
   参照解答と自然な別解は、[Docker統合テストの実行条件](../backend/tests/integration/README.md)を
   満たすrootless sandboxで確認します。ホストやbackendのshellでは実行しません。
   誤りの例も意図どおり区別できるか確かめ、入力の不足と判定の制約を分けて評価します。
7. 新問も対象となる全問題回帰を実行します。sandboxや表示機能も変更した場合は、その回帰も追加します。
   日英の問題文、入力・想定出力・画像、実提出の結果をPCとスマートフォン幅で確認します。
   repositoryは起動時に固定されるため、画面確認前にbackendとrunnerへ同じ更新を反映します。
8. 「作成後に残す短い記録」に従って、採用した設計意図を文書に保存します。
   設計意図、既存問題との差、実施・未実施の検証、変更ファイルを報告し、diffをレビューに残します。
   commitは[作業規約](../AGENTS.md)に従います。

### 新規追加・意図した修正と移行baseline

現状は[問題schemaテスト](../backend/tests/test_problem_schema.py)がlegacyとv3のID一致と
決定的な移行結果を、[問題データテスト](../backend/tests/test_problem_data.py)がlegacyの
semantic manifestや画像数を検証します。[repositoryテスト](../backend/tests/test_problem_repository.py)にも
現在の問題数の期待値があります。v3へYAMLと画像を増やすだけでは、これらの検査を通りません。

将来の追加時は、既存の移行済み問題を保護する検査と、増減する現行問題セットの検査を
どう分けるかを変更範囲として提示してください。意図した既存問題の修正も、対応する移行一致の
期待値が影響を受けます。単にテストを削除したり、件数だけを書き換えて済ませたりしません。
`yaml_data/`と`semantic_manifest.json`を新問の投入先として機械的に更新したり、
legacyからの一括再生成で編集済みv3を上書きしたりしてはいけません。
移行前の意味を保護しつつ、どの差分を意図して許容するかをレビューできるようにします。

### 完了前の確認

- 学びを一文で説明でき、入力と道具の機能が自然につながっている。
- 単純作業なら基礎練習として位置付け、既存問題との差を説明できる。
- 日英とも条件が明確で、想定解に都合のよい前提を隠していない。
- 自然な別解、典型的な誤解、期待出力の独立した確認を検討している。
- 作成した問題の設計意図を問題ID付きで文書に残し、修正時も内容を同期している。
- 現行の画面・実行環境・判定で成立し、未検証の内容を検証済みと説明していない。
- 関係する検査・manifest・文書が整合し、無関係な問題や隔離設定を変更していない。
